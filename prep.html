1. What virtualization is

The one-sentence idea

A virtual machine (VM) is a computer running inside another computer. The inner computer (the guest) believes it has its own CPU, memory, disk and network. Really, a program on the outer computer (the host) gives it all of these.

Analogy: a play on a stage. The actor (the guest Linux) plays the scene for real. When the actor reaches for a prop that isn't really there, like a phone or a door, a stagehand (your program) hands it over. Then the actor carries on.

The four layers, top to bottom

Guest: Linux 6.12not my code

An ordinary Linux kernel. It doesn't know it's in a VM. It's treated as untrusted.

VMM: microvm-rs (my program)what I built

A normal Rust program, run as a normal user. It sets up the machine and pretends to be the devices: the console, the disk and the network card.

KVM, inside the Linux host kernelalready in Linux

The part of Linux that switches the CPU into its special "run a guest" mode. My program talks to it through /dev/kvm.

Hardware: CPU with Intel VT-xthe real machine

Modern CPUs can run guest code directly at full speed, and stop it whenever it touches something that should be hardware.

Hypervisor = KVM + VMM together. I wrote the VMM half. Firecracker (from AWS, used by Lambda) and QEMU are other VMMs that use KVM.

The heart of it: the VM exit loop

This is the single most important idea. If you can explain this, you can explain the project.

  1. My program asks KVM: "run the guest" (the KVM_RUN call).
  2. The guest runs on the real CPU at full speed: normal code, maths, memory access.
  3. The guest touches "hardware", for example it writes a character to the serial port. The CPU stops the guest. This is a VM exit.
  4. KVM hands the exit to my program: "the guest wrote 'A' to port 0x3f8".
  5. My program does the job (prints 'A' on the terminal) and calls KVM_RUN again. Back to step 2.
Say itThe guest runs directly on the CPU. Whenever it touches a device, the CPU stops it and KVM tells my program what it wanted. My program emulates that device and resumes the guest. That loop is the core of every VMM.

Words you will hear

Host / guest
Host = the real machine (your laptop, WSL2). Guest = the Linux running inside the VM.
vCPU
A virtual CPU. In my VMM each vCPU is one thread that loops on KVM_RUN.
ioctl
The system call used to talk to KVM: "create a VM", "set registers", "run".
Guest memory
A block of the host's memory that I hand to KVM as the guest's RAM.
Interrupt (IRQ)
A device's way of saying "I have something for you", e.g. a key was pressed or the disk read finished.
Serial console
The simplest text in/out device (an emulated 16550 UART, COM1). Linux prints its boot log through it.
virtio
A standard for "fake" devices designed for VMs, so they're fast and simple. I built a virtio disk and network card.
bzImage / initrd
The compressed Linux kernel file, and a small starter file system loaded with it.
Real / long mode
CPU modes. Real mode is the 16-bit mode from 1978; long mode is modern 64-bit.
Triple fault
The CPU fails so badly it resets. In a VM it shows up as a "shutdown" exit; usually it means a setup bug.
seccomp
A Linux feature that limits which system calls a program may make. Anything else kills the program.

2. Your project in 60 seconds

Answer to "Tell me about your project." Learn the shape, not the exact words.

Say it

microvm-rs is a small virtual machine monitor written in Rust, in the style of Amazon's Firecracker. It uses Linux KVM.

It boots a normal Linux kernel in about four seconds. The guest gets a virtual disk, which is a file on the host, a virtual network card, and up to four CPUs.

KVM does the hard CPU and memory work. My program does the rest: it gives the guest its memory, loads Linux like a boot loader, and pretends to be the devices.

I treated the guest as an attacker, so everything it sends me is checked, and every thread runs under a seccomp filter that limits what it can do on the host.

I built it in two phases, using spec-driven development: a written spec with pass/fail tests, then a plan, then one milestone at a time, with a script that checks every requirement.

Phase 1 and Phase 2 in one line each

  • Phase 1, boot Linux: run tiny test programs in 16-bit and 64-bit mode, then boot a real Linux kernel with a serial console you can type into. Reboot inside the guest cleanly exits the VMM.
  • Phase 2, a useful machine: add a virtio disk, a virtio network card, up to 4 vCPUs, and seccomp filters.
  • Phase 3 (not built): confidential VMs (AMD SEV-SNP / Intel TDX). These need special hardware.

3. The parts you built

For each part: what it does in plain words, and the one reason behind it. The reason is what an examiner tests.

Booting Linux Phase 1

There's no BIOS. My program does the boot loader's job. It copies the Linux kernel into guest memory at 1 MiB, writes an info page (boot_params: how much RAM, the command line), builds page tables, and puts the CPU straight into 64-bit mode. Then it starts the vCPU at the kernel's entry point.

Why: it's simpler and faster than emulating firmware. Firecracker does the same.

Serial console Phase 1

An emulated UART at port 0x3f8. When Linux writes a character there, that's a VM exit, and I print it. A separate thread reads your keyboard, puts keys into the UART and raises interrupt 4.

Why a separate thread: when the guest is idle, the vCPU thread is asleep inside KVM, so it can't also read the keyboard.

virtio disk Phase 2

The guest sees a disk /dev/vda. It's really a 64 MiB file (disk.ext4) on the host. Data written in the guest stays in that file after the VM stops.

Why virtio instead of faking a real disk chip: real hardware needs many VM exits per operation. virtio puts requests in shared memory and needs one "doorbell" per batch.

How virtio works the queue

The guest and my program share a virtqueue in guest memory. The guest writes a request ("read sector 8 into this buffer") and rings a doorbell. I read the request, do the file I/O, write back the result, and raise an interrupt.

Key point: the guest controls that memory, so I check every field: is the buffer inside RAM? Is the sector inside the disk? Does the chain of buffers loop forever?

virtio network Phase 2

The guest gets a network card eth0. On the host it's connected to a TAP device (vmtap0, 172.16.0.1), which is like a virtual network cable. The guest can ping the host.

Why sudo is needed once: creating the TAP needs admin rights (setup-tap.sh). After that, the VMM itself runs as a normal user.

Multiple CPUs Phase 2

Up to 4 vCPUs, one thread each. I write an MP table into guest memory, which is a small table that tells Linux how many CPUs there are. CPU 0 starts first; Linux then wakes the others.

Hard part: shutting down. Idle vCPUs are asleep inside KVM, so I send each thread a signal to wake it, then wait for it to finish.

seccomp filters Phase 2

Each thread gets a list of allowed system calls. For example, only vCPU threads may run the guest, and only the main thread may read and write the disk file. Nobody may open files or start programs. Anything outside the list kills the whole VMM.

Why: if a guest ever exploited a bug in my program, it still couldn't do much on the host.

Why Rust?

A VMM reads data from an untrusted guest. In C, one mistake there (a buffer overflow) can let the guest escape onto the host. Rust prevents that whole class of bugs. The few places that need unsafe (19 blocks, mostly talking to KVM) each have a comment explaining why they're safe.

4. How you built it

Say it

I used spec-driven development with an AI coding agent, Claude Code. In short: write down what it must do, then build it in small steps, then check every requirement.

  • Spec: a document listing what the VMM must do, with pass/fail tests (57 in total).
  • Small steps: 8 milestones. I approved each one before the next started, and every design choice was written down with its reason.
  • Check: a script runs all the tests and prints PASS or FAIL for each.

One problem I hit: after a Windows update, one test passed even with the feature switched off. I fixed the test so it can really fail.

"Did you write this yourself?"

Expect this. Answer honestly and the same way every time. Adjust this template so it's true for you:

I used Claude Code as a coding agent, which is what the course teaches. I owned the specs and the acceptance criteria, answered the design questions, and approved each plan and milestone. The agent wrote most of the code against those specs. My job is to be accountable for it: I can explain why each part is designed the way it is.

When you don't know an answer

  • "I don't remember the exact detail, but the idea is…" Then give the plain-language version from this page.
  • "That part is handled by KVM, not my code. What my code does is…"
  • "That's out of scope for this phase. The spec lists it as out of scope, for example snapshots or a jailer."
  • "I'd check DECISIONS.md. Every design choice is logged there with the options and the reason."

Never guess a number. Say "about" or "I'd have to check."
