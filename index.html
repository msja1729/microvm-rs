The 60-second answer

"Tell me about your project." Practise until you can say this without reading. Keep the numbers exact; a professor notices rounding.

microvm-rs is a minimal virtual machine monitor in Rust, in the style of Firecracker, built on Linux KVM. It boots an unmodified Linux 6.12 kernel in about four seconds, with a virtio disk backed by a host file, a virtio network card backed by a TAP interface, and up to four vCPUs.

KVM does the CPU and memory virtualization inside the kernel. My process does everything else: it lays out guest memory, puts the vCPU straight into 64-bit long mode, acts as the boot loader, emulates the serial port and the virtio devices, and describes the machine to Linux with an MP table and per-vCPU CPUID.

The guest is treated as hostile. All code that parses guest data is written as pure functions, proven with the Kani model checker and fuzzed, and every VMM thread runs under its own seccomp allowlist, so a forbidden syscall kills the process.

I built it spec-first: two phase specs with 57 pass/fail acceptance criteria, an approved plan per phase, eight milestones, 72 logged decisions, and a verify script that checks every criterion. It runs as a normal user, and v0.2.0 is on GitHub with a one-command run.sh.

The 2-minute follow-up: one request, end to end

If they say "go deeper", trace one disk read. It touches every layer and shows you understand threads, KVM and the untrusted-input story.

  1. The guest's virtio_blk driver puts three descriptors in RAM (16-byte header, data buffer, 1-byte status), publishes the head in the available ring and writes 0 to QueueNotify at 0xd000_0050.
  2. KVM matches that write against the ioeventfd registered for queue 0 and signals it. The guest resumes immediately; no exit to user space.
  3. The main thread wakes in epoll_wait, locks the transport, and Queue::pop reads avail.idx and the ring slot, each checked.
  4. walk_chain copies each descriptor out once (at most queue-size of them). parse_blk_request checks directions, RAM ranges and sector × 512 + len ≤ disk size with checked arithmetic.
  5. The device preads through a 64 KiB bounce buffer into guest RAM, writes the status byte, the used element, a release fence, then used.idx.
  6. It sets InterruptStatus bit 0 and writes the irqfd: KVM raises IRQ 5 through the IOAPIC.
  7. The guest's handler reads InterruptStatus and writes InterruptACK. Those are MMIO exits on the vCPU thread, served from an atomic without the transport lock.

Fix the spec, not the code: your best story

AC-8.2(d) said a chain that revisits a descriptor index is rejected. Kani's counterexample: head 0 has NEXT → 0, and between the two reads the guest rewrites descriptor 0 so the second copy has no NEXT. The walker accepts a 2-descriptor chain.

That isn't a safety bug. Each descriptor is read once into a local copy and checked, and the walk is still bounded by the queue size. Patching the code with a visited-set would add state for no safety gain. Instead the spec now states two properties: the walk always ends within the queue size, and a revisit is rejected when the table is stable. The harness proves both.

Say it like thisThe proof told me my spec claimed something stronger than what's true under concurrency. I changed the claim, not the code, and the commit says why.

Scope creep: concrete refusals

  • D3: --mode long was kept out of the CLI during M1, so M2 added the flag together with its implementation.
  • D9: the MP table waited for M6, even though M4's IRQs could have used it. M4/M5 used the existing PIC path.
  • D12, D46: test helpers were duplicated rather than adding tests/common/, and fuzz/Cargo.lock stays ignored, because neither file is in the spec's output list.
  • D7: verify-phase-1.sh grew one milestone at a time instead of being written up front.
  • Each spec has an explicit "Out of scope" list: snapshots, API socket, jailer, PCI, ACPI…

Outcome vs. trajectory evaluation

The verify scripts are outcome evaluation. Plan approval, per-milestone review and the decision log are trajectory evaluation.

Your project has an example where outcome alone lied. After a WSL2 update every process ran under an inherited seccomp filter, so AC-7.1's test (Seccomp: 2 on every thread) passed even with no VMM filter. D48 changed the test to count filters against the inherited baseline, so it can no longer pass vacuously.

CLAUDE.md and the extension toolkit

Your CLAUDE.md holds the rules that must shape every session: read the specs first, one milestone at a time, never edit a SPEC.md without asking, stop and propose a spec change on ambiguity, log every in-scope choice, ask before new crates or sudo. Auto memory recorded the GitHub/release facts.

Likely follow-up: "which rule should be a hook?" Answer: fmt and clippy at every commit. A rule that must hold every time belongs in a pre-commit hook, not prose (Ch. 13.5.5 and 13.9).

Where SDD struggled here

Three tasks were discovery, not specification, which matches the chapter's "contractor, not researcher" point:

  • The seccomp allowlists could not be written from the code; they came from strace -f traces, which found TCGETS inside glibc's tcsetattr (D36).
  • Kani bounds: the spec had a fallback (queue size 2) in case proofs ran over 20 minutes (Q5). A harness took 15+ minutes until symbolic-length heap data was removed (D43).
  • Kani's counterexample (above) showed the spec's own claim needed refining.

Reversibility

Irreversible or privileged steps stayed with the human. The agent can't sudo, so the TAP is created once by the user with sudo scripts/setup-tap.sh, and the VMM only opens it. setup-tap.sh refuses to delete a foreign vmtap0 (D31). Tests always use a temporary copy of the disk image, and the fuzzer runs on a temporary copy of the corpus.

The chapter's checkpoint questions, answered with this project

13.3 analog. "A test fails: /sys/block/vda/size prints 131070, not 131072. First question?" Is the spec's number right? 64 MiB / 512 = 131072, so the spec is right and the implementation's capacity is wrong. If the spec had been ambiguous (say, bytes vs. sectors), the fix would go in SPEC.md first.
13.4 analog. "It boots, so you're done?" No: passing AC-6.4 says it boots ten times, not that you can explain why APs wait for SIPI. Do the walkthrough (Architecture tab) and the drill without notes.
13.1 analog. Vibe coding vs SDD here: a VMM that mis-parses one descriptor gives the guest host memory access. The cost of being wrong is a security hole, not a re-run, so SDD was the right call from day one.
Worked problem 13.3 analog. Read your log bottom-up: Phase 2 spec placeholder → spec → spec review fixes → plan + D1–D18 → M4 … M8 → spec clarification → test fix. Spec before plan before code.

Live demo script

From the release tarball, so you show exactly what the professor downloaded. Rehearse it once on the machine you'll present from. Note that run.sh boots with --disk disk.ext4, so writes in the guest change the bundled image.

1. Install and boot (≈ 4 s)

# verify the download, unpack, boot with 2 vCPUs and the disk
sha256sum -c SHA256SUMS
tar xzf microvm-rs-v0.2.0-x86_64-linux.tar.gz && cd microvm-rs-v0.2.0-x86_64-linux
VCPUS=4 ./run.sh

2. Inside the guest: prove each milestone

echo vmm-$((6*7))                 # M3: keystrokes reach the guest (IRQ 4 via irqfd)
uname -r                          # 6.12.x
nproc; grep LOC /proc/interrupts  # M6: 4 CPUs, each taking timer interrupts
cat /sys/block/vda/size           # M4: 131072 sectors = 64 MiB
mkdir -p /mnt && mount /dev/vda /mnt && cat /mnt/hello.txt   # phase2-disk
echo persist-ok > /mnt/p.txt && sync && umount /mnt
reboot -f                         # i8042 reset → VMM exits 0, terminal restored

Boot again and cat /mnt/p.txt after mounting: persistence across a new VMM process (AC-4.5).

3. From a second terminal while it runs: show seccomp

for t in /proc/$(pgrep -x vmm)/task/*; do
  echo "$(cat $t/comm): $(grep -E 'Seccomp_filters|NoNewPrivs' $t/status | tr '\n' ' ')"
done

Threads vmm, stdin, vcpu0..3, plus KVM's kvm-nx-lpage-recovery worker. On WSL2 expect one more filter than a plain shell has (D48).

4. The small programs and the failure paths

./vmm raw --image hello16.bin --mode real; echo "exit $?"   # Hello from real mode! · exit 0
./vmm raw --image hello64.bin --mode long; echo "exit $?"   # Hello from long mode! · exit 0
./vmm boot --kernel bzImage --vcpus 5; echo "exit $?"       # rejected · exit 2
./vmm boot --kernel bzImage --initrd initramfs.cpio --seccomp-test-violation
echo "exit $?"   # 159 = 128 + SIGSYS(31): killed by the vCPU filter (AC-7.4)
stty sane        # SIGSYS can't be caught, so the terminal is left in raw mode

Run the violation demo last. If the terminal stops echoing, type stty sane and press Enter even if you can't see it. That this happens is itself a talking point: the spec exempts SIGSYS and SIGKILL from "always restore the terminal".
