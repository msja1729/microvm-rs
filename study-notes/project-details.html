The project in one picture

We wrote a program called vmm that makes a pretend computer inside your real computer. A whole Linux runs inside it and thinks it owns a real machine.

KVM does the fast part (running guest code on the real CPU). Our vmm does everything else.

Who does what

PartJob in one line
KVM (in the host kernel)Runs the guest's instructions directly on the real CPU, and stops when the guest touches something it can't handle.
vmm (our Rust program)Builds the pretend machine: memory, CPUs, disk, network, serial console. Answers whenever KVM stops.
Guest (Linux 6.12)An ordinary, unmodified Linux kernel and a BusyBox shell. It never knows it is pretend.
"VMM" means Virtual Machine Monitor. KVM is the hypervisor part inside the kernel; the VMM is the user-space program that drives it. QEMU, Firecracker, Cloud Hypervisor and crosvm are all VMMs that sit on top of KVM. Ours is a small Firecracker-style one.

The problem: strangers' code on your computer

A cloud company runs code from thousands of strangers on the same machine. Any one of them might be an attacker. How do you keep each one in its own room?

Three things everyone wants at once

WantWhy
Strong walls (isolation)If C breaks out, it can read A's and B's data. That ends a cloud business.
Fast startServerless functions start on demand. Users notice seconds of delay ("cold start").
Tiny size (density)More rooms per server = less hardware per customer = cheaper.

The old tools gave you two of the three. The next page shows why.

3

Three ways to build walls

The trick of a microVM: keep the strong wall of a real VM, but throw away every device a cloud server doesn't need. Less code = fewer places to break in, and faster boot.
"A container is a small VM." No. A container is a normal process with kernel-enforced limits; every container shares the same host kernel. One kernel bug can break every wall at once. A VM gives each tenant its own kernel, and the only shared surface is KVM plus the VMM.
4

Who uses this in industry

The same shape as our project (KVM + a small Rust VMM) is running in production at large scale.

FirecrackerAmazon Web Services

Built for AWS Lambda and Fargate. Each function call runs in its own microVM. Open-sourced 2018. The model for our project.

Cloud HypervisorIntel, Microsoft, others · Linux Foundation

A Rust VMM for modern cloud workloads. Shares the rust-vmm crates we use.

crosvmGoogle

Runs Linux apps on ChromeOS and protected VMs on Android. The original Rust VMM that Firecracker grew from.

Kata ContainersOpenInfra

Looks like a container to Kubernetes, but each pod is secretly a microVM. Can use Firecracker or Cloud Hypervisor.

Fly.io and similar hostsapp platforms

Run customers' apps as Firecracker microVMs around the world.

AI code sandboxese.g. E2B and agent platforms

When an AI agent writes code and runs it, that code is untrusted. Many sandboxes put each run in a microVM.

We build on the same rust-vmm crates these projects share: kvm-ioctls, vm-memory, linux-loader, vm-superio, seccompiler, event-manager. Learning this repo is learning their building blocks.

Why now, and what they are chasing

What the industry is trying to achieve

GoalHow it shows up in our project
Smallest possible attack surfaceOnly serial, i8042 (for reboot), virtio-blk, virtio-net. No PCI, no ACPI, no BIOS.
Boot in a blinkWe load the Linux kernel directly into guest RAM and jump in. No firmware step.
Assume the VMM itself might get hackedM7: seccomp lets each thread make only the system calls it needs. Anything else kills the VMM.
Prove, don't hopeM8: Kani proves the guest-facing parsers can't panic or read out of bounds; a fuzzer throws millions of random inputs at them.
Hide the guest from the hostPhase 3 (not started): AMD SEV-SNP / Intel TDX encrypt guest RAM.

Our road: Phase 1 → 2 → 3

What each step adds, in kid words

StepBeforeAfter

M3Only tiny programs.Real Linux runs; you type commands in a shell.

7

The one rule: the guest is a stranger

Every number the guest hands us (an address, a length, an index) might be a lie. We check it before we use it. The guest must never be able to crash, hang, or trick the VMM.
This rule is written in the project SPEC.md: "A guest is untrusted: nothing a guest does (any port write, any MMIO access, any byte value) may panic the VMM."
